# 第5章 记忆系统

> 源码位置：`src/agentscope/middleware/_longterm_memory/_mem0/`（长期记忆）、`src/agentscope/app/middleware/_inbox_middleware.py`（跨 agent）、`src/agentscope/state/_state.py`（短期）、`src/agentscope/app/middleware/_state_change_middleware.py`（状态变更）。这一章回答："agent 怎么记住过去的事？"

## 一、概念引入

"记忆"在 agent 里是个被滥用的词。要讲清楚，得先分层。AgentScope 实际上有**五层**记忆，各司其职：

| 层 | 存哪 | 机制 | 检索方式 | 持久化 |
|----|------|------|---------|--------|
| 短期（工作记忆） | `state.context` | list[Msg] | 顺序（全量喂模型） | 内存，Msg 镜像到 storage |
| 压缩摘要 | `state.summary` | LLM 结构化摘要 | 作为 UserMsg 前置 | 随 state 持久化 |
| 长期（语义） | mem0 向量库 | embedding 检索 | 语义相似度 | mem0 后端（Qdrant） |
| 跨 agent（inbox） | message bus 队列 | ack-on-read drain | 精确投递 | Redis stream，TTL |
| 状态变更 | 事件总线 | MD5 哈希对比 | 事件通知 | 瞬时（replay log） |

💡 关键认知：**前两层（context/summary）是"把过去塞进 prompt"，后三层是"按需取/被通知"**。短期记忆成本高（占 token）但最准确；长期记忆省 token 但靠召回质量。

## 四、源码剖析

### 问题 1：mem0 的存取

长期记忆完全基于 [mem0](https://github.com/mem0ai/mem0)（opt-in，需装 `mem0ai`）。`Mem0Middleware`（`_middleware.py`）是核心。

**存（add）**——`_async_add`（`_middleware.py:536`）：
```python
await client.add(
    messages=[{"role":"user",...}, {"role":"assistant",...}],
    user_id=..., agent_id=..., infer=True
)
```
mem0 内部会用 LLM **提炼**（infer）出"值得记的事实"再存向量库，不是原样存整段对话。

⚠️ mem0 的提炼可能"提炼不出东西"（比如纯寒暄）。所以有 `_async_add_with_fallback`（`:571`）：先 `infer=True` 试，若 `_mem0_extracted_anything`（`_utils.py:41`）判断啥也没提炼出来，再用 `infer=False` 把原文直接存。docstring（`:584-618`）解释了这是为了兼容当前 mem0 按 filters 而非 role 选 prompt 的行为。

**取（search）**——`_async_search`（`_middleware.py:522`）：
```python
results = await client.search(
    query=查询文本,
    filters={"user_id": ..., "agent_id": ...(可选)},
    top_k=..., threshold=...
)
```
检索按 `user_id`（+可选 `agent_id`）隔离——不同用户的记忆互不可见。

### 问题 2：检索结果怎么进 prompt

`on_reply`（`_middleware.py:285-374`）的流程：

1. **reply 前检索**：从 `input_kwargs["inputs"]` 提取查询文本（`_extract_query_text`，`_utils.py:16`）。
2. 调 `_async_search` 拿到记忆条目。
3. **在 ReplyStartEvent 之后**（即用户消息已被 agent 吸收，但 reasoning 循环还没开始），把记忆注入 `state.context`（`:353-362`）。
4. **reply 后写回**：`finally` 块里把"用户提问 + 助手回答"这对存进 mem0（`:363-374`）。

🔑 记忆注入用 `_build_memory_message`（`:642`）渲染成 **assistant 角色的 `Msg(name="memory")`，内容是一个 `HintBlock`**。

💡 为什么是 assistant 角色 + HintBlock？看第1章：**user 消息不能携带 HintBlock**。而 HintBlock 在格式化时会转成 user message 给模型看。所以"模型实际看到的是 user 角色的记忆提示，但在 context 里它以 assistant+HintBlock 形式存在"——这是为了让记忆和真实用户发言在数据结构上区分开。

记忆内容是 markdown 列表，带 `DEFAULT_MEMORY_SECTION_HEADER`（`:71`）：
```
## Memory
- 用户偏好用 Python
- 上次任务做到第3步
```

### 问题 3：自动管 vs agent 自决

`Mem0Middleware` 支持三种 `mode`（`_middleware.py:151`）：

| mode | 行为 | 暴露工具 |
|------|------|---------|
| `static_control` | 中间件**自动**每次 reply 前检索、后写回 | 否 |
| `agent_control` | 中间件不自动检索，**agent 自己决定**何时查/存 | `search_memory`/`add_memory` |
| `both`（默认） | 两者都开 | 是 |

`agent_control` 模式下，`on_reply` 是纯透传（`:297-300`），agent 通过 `search_memory`（`_tools.py:61`，`is_read_only=True`）和 `add_memory`（`:151`）工具主动操作。这让 agent 能"判断当前是否需要回忆"，省 token。

🔑 这是个重要的设计取舍：**static 省心但每次都检索（费 token/延迟）；agent_control 灵活但依赖模型判断力**。`both` 是默认的稳妥选择。

### 问题 4：跨 agent 消息投递

这是多 agent 协作的基础（第7章详讲调度，这里讲"记忆"视角）。核心是 **inbox 机制**：

**发送方**（`TeamSay` 工具，`_tools/_team_say.py:284-311`）：
```python
hint = HintBlock(hint=f'<team-message from="{sender}">\n{content}\n</team-message>',
                 source=sender)
payload = hint.model_dump(mode="json")
for sid, aid in recipients:
    await message_bus.inbox_push(sid, payload)      # 推到对方 inbox 队列
    await message_bus.enqueue_wakeup(user_id, sid, aid)  # 唤醒对方
```

**接收方**（`InboxMiddleware.on_reasoning`，`_inbox_middleware.py:57-136`）：
1. 在**每次 reasoning 步骤开头**，`inbox_drain(session_id)`（`:81`）把队列里所有消息取走（ack-on-read，每条只取一次）。
2. 反序列化成 `HintBlock`（`:87`）。
3. 注入 `state.context`（`:101-123`）：如果最后一条是自己的 assistant 消息，就把 hint 追加到它的 content；否则新建一条 assistant 消息装 hint。
4. 对每个 hint 发一个一次性的 `HintBlockEvent`（`:127`），让前端实时渲染。

🔑 关键时序：**消息不是"一发就到"，而是"对方下次 reasoning 时才 drain"**。inbox 是队列，消息在对方空闲时堆积，等对方被唤醒开始跑才注入。这就是为什么发送方要 `enqueue_wakeup`——否则对方不会主动 reasoning，消息永远躺着。

💡 这种"投递 + 唤醒"的解耦，让跨 agent 通信天然异步、跨进程可行（inbox 在 Redis，wakeup 信号广播给任意进程的 dispatcher，见第7章）。

### 问题 5：状态变更通知

`StateChangeMiddleware`（`_state_change_middleware.py`）实现 `on_acting`（`:84`），在**每个工具执行前后**对比状态：

1. 工具执行前：`hash_before = _state_hash(agent)`（`:106`）。
2. 执行工具（透传其输出）。
3. 执行后：`hash_after = _state_hash(agent)`（`:112`）。

`_state_hash`（`:62`）对 `tasks_context` + `permission_context` 的 `model_dump_json()` 算 MD5。⚠️ docstring（`:67`）明确**不包含 context**——因为 context 每步都变，不是这里要追踪的。

- 哈希变了 → 发 `CustomEvent(name="state_updated")`（`:112-130`），含变化后的 tasks/permission 上下文。
- 工具名是 `TeamCreate`/`AgentCreate`/`TeamDelete` → 发 `CustomEvent(name="team_updated")`（`:133-141`），因为这些工具直接改 storage。

这些事件发到 message bus，前端 SSE 订阅后刷新 UI（任务列表、团队成员变化实时显示）。

💡 为什么用 MD5 对比而不是直接发"变更后状态"？因为不是每个工具都改状态，哈希对比能**只在真变了时才通知**，避免噪音。

### 补充：mem0 与 AgentScope 的桥接

mem0 的 LLM/Embedding 接口是**同步**的，但 AgentScope 的模型是异步的。`_agentscope_adapter.py` 解决这个阻抗：

- `AgentScopeLLM`（`:94`）实现 mem0 的 `LLMBase.generate_response`，内部委托给 AgentScope ChatModel。
- `AgentScopeEmbedding`（`:231`）实现 `EmbeddingBase.embed`。
- `_AsyncBridge`（`:63`）开一个**守护线程的事件循环**，用 `run_coroutine_threadsafe` 把异步调用桥到同步接口——因为 mem0 在自己线程里同步调。
- `_register_agentscope_provider`（`:386`）把这两个适配器注册进 mem0 的工厂，绕过 mem0 硬编码的 provider 白名单。

💡 这是个经典的"同步框架套异步库"的桥接模式，值得学习：**守护线程 + run_coroutine_threadsafe**。

## 六、本章小结

```
                  ┌─ 短期: state.context （全量进 prompt，第4章压缩它）
                  ├─ 摘要: state.summary （压缩产物，前置进 prompt）
agent 的过去 ─────├─ 长期: mem0 向量库 （语义检索，opt-in 中间件）
                  ├─ 跨agent: inbox 队列 （精确投递 + 唤醒，第7章）
                  └─ 变更: 事件通知 （MD5 对比，前端刷新）
```

🔑 四句话：
1. **五层记忆各司其职**：context/summary 进 prompt，mem0 语义检索，inbox 精确投递，事件通知变更。
2. **长期记忆靠 mem0**，存时 LLM 提炼、取时 embedding 检索，按 user_id 隔离；检索结果以 assistant+HintBlock 注入。
3. **跨 agent 消息是"投递 + 唤醒"异步模型**，接收方下次 reasoning 才 drain，天然跨进程。
4. **记忆注入统一用 HintBlock**——框架"在对话里夹带私货"的通道（第1章已铺垫）。
