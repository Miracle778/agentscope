# 第4章 上下文管理与压缩

> 源码位置：`src/agentscope/agent/_agent.py`（`compress_context` 及相关方法）、`src/agentscope/agent/_config.py`（`ContextConfig`）、`src/agentscope/workspace/`（offload）。这是用户最关心的主题之一：**上下文超了怎么办**。

## 一、概念引入

LLM 有 context window 上限（如 GPT-4o 128K、Claude 200K）。但一个长时间运行的 agent 会不断累积消息：

- 每轮 reasoning 的思考、每次工具调用和结果，都写进 context。
- 一次 `cat big_file.txt` 的工具结果可能就是几万 token。

如果不处理，context 会撑爆 window，API 报错。业界的几种做法：

| 方案 | 做法 | 缺点 |
|------|------|------|
| 滑动窗口 | 只保留最近 N 条 | 丢失早期关键信息 |
| 摘要压缩 | 把旧消息让 LLM 总结成摘要 | 摘要可能丢细节 |
| 向量检索 | 旧消息存向量库，按需检索 | 实现复杂、召回不准 |

AgentScope 采用 **摘要压缩 + offload（卸载）** 的组合：

- 旧消息让模型生成**结构化摘要**（不是自由文本），存进 `state.summary`。
- 被压缩掉的原始消息**不直接丢弃**，而是 offload 到 workspace 文件，summary 里留一个引用路径，模型需要时可再读。
- 单个工具结果过大时，单独截断 + offload 尾部，留一个 `<<<TRUNCATED>>>` 提示。

## 三、经典问题

1. context 到底存在哪？system prompt 算不算 context？
2. 压缩什么时候触发？阈值是多少？
3. 压缩时"哪些留、哪些压"怎么决定？工具调用和结果被切开会怎样？
4. 摘要是自由文本还是结构化的？压缩失败怎么办？
5. 一个工具结果特别大（比如读了 10MB 文件），怎么处理？
6. "压缩"和"后台 offload 慢工具"是一回事吗？

## 四、源码剖析

### 问题 1：context 的结构与累积

🔑 **context = `state.context: list[Msg]`**（`state/_state.py:151`）。system prompt **不**存在 context 里，每次模型调用时由 `_prepare_model_input`（`_agent.py:2004`）临时拼到最前面：

```
模型实际输入 = [SystemMsg] + [summary 的 UserMsg（若有）] + state.context
```

消息怎么累积？看 `_save_to_context`（`_agent.py:2183-2255`），关键设计（docstring 在 `:2196`）：

> **一个 reply 产生一个 `AssistantMsg`**，其 `id == state.reply_id`。

在一次 reply 的 ReAct 循环里：
- 第一次产出 → 新建 `AssistantMsg` 追加（`:2226`）。
- 后续的 reasoning 文本、`ToolCallBlock`、`ToolResultBlock` → **都追加到这同一条 AssistantMsg 的 content 列表**（`:2236`），token 用量累加到 `usage`。
- 下一次 reply 才新建新的 AssistantMsg。

💡 这样设计的好处：一条 reply 在 context 里是**一个原子单元**，压缩切分时更容易按"整条消息"为单位处理，不会把一次回复的思考肢解。

### 问题 2：压缩触发时机

`compress_context`（`_agent.py:258`）在每次 reasoning 步骤**开头**被调用（`_agent.py:608`）。核心逻辑在 `_compress_context_impl`（`:299`）：

```python
estimated_tokens = await self.model.count_tokens(**kwargs)   # _agent.py:315
threshold = cfg.trigger_ratio * self.model.context_size      # :319
if estimated_tokens < threshold:
    return   # 没超阈值，跳过                                    # :320
```

🔑 阈值参数（`ContextConfig`，`_config.py:51`）：
- `trigger_ratio`：默认 **0.8**（`:57`），约束 `0 < x < 0.9`。即 context 用到 80% 才触发。
- `reserve_ratio`：默认 **0.1**（`:62`），压缩后保留最近 10% 的消息。
- `< 0.9` 的上限是给压缩调用本身留 headroom（压缩也要消耗 token）。

⚠️ `count_tokens` 是粗估（字节数/4，见第3章），所以实际可能比估计多。这就是为什么 `trigger_ratio` 不是 1.0。

### 问题 3：切分策略——保留与压缩

`_split_context_for_compression`（`_agent.py:1699-1800`）决定"哪些留、哪些压"：

1. **SystemMsg + 已有 summary 永远保留**（`:1719`）。
2. **从 context 末尾往前走**，累计 token，直到保留部分的 token 数超过 `reserve_ratio * context_size`（`:1729-1739`）。
3. 切分点之前 → `msgs_to_compress`（要压缩的旧消息）；之后 → `msgs_to_reserve`（保留的近期消息）。

⚠️ 但切分点可能落在一条消息的中间，于是有 **block 级切分**（`:1750-1767`）：把边界那条 `Msg` 深拷贝成两半，按 block 精确切。

🔑 **工具调用配对保护**（`:1769-1784`）——这是最容易踩坑的地方：

> 如果一个 `ToolResultBlock` 被保留，但它的 `ToolCallBlock`（模型说要调工具的那条）被分到压缩侧，这个结果就成了"孤儿"——模型看到工具结果却不知道为什么调。这会让 API 报错。

所以切分后会扫描保留侧：任何"对应 tool_call 不在保留侧"的 `ToolResultBlock`，连同它一起被推到压缩侧，**保证 tool_call 和 tool_result 永远在同侧**。

```
压缩侧        | 保留侧
────────────────────────────────
... 旧消息 ... | [ToolCall X] [ToolResult X] [最近消息]   ✅ 配对完整
              |
若切在这里 →  | [ToolResult X] [最近消息]   ❌ 孤儿结果
              | → 自动把 ToolResult X 也推到压缩侧
```

如果切分后发现 `msgs_to_compress` 为空（reserve_ratio 太大），会**回退到 reserve=0 重新切**并 warning（`:354-369`）。

### 问题 4：摘要生成与失败回退

切分后，对 `msgs_to_compress` 调用模型生成摘要（`_agent.py:422`）：

```python
res = await self.model.generate_structured_output(
    messages=msgs_system + msgs_to_compress + [UserMsg(compression_prompt)],
    structured_model=cfg.summary_schema,
)
self.state.summary = cfg.summary_template.format(**res.content)   # :469
```

🔑 摘要是**结构化的**（第3章的 `generate_structured_output`）。`SummarySchema`（`_config.py:9-46`）字段：`task_overview`、`current_state`、`important_discoveries`、`next_steps`、`context_to_preserve`——比自由文本摘要更稳定、信息更全。

💡 摘要通过 `summary_template`（`:85`）渲染成文本存进 `state.summary`，下次模型调用时作为一条 UserMsg 放在 system prompt 之后（见问题1）。

**失败回退**（`_agent.py:429-466`）——如果压缩调用本身都溢出了（要压缩的内容 + 系统 prompt 仍超 window）：

```
while 估计压缩调用 token > context_size:
    从 msgs_to_compress 丢掉最旧的一条（msgs_to_compress[i:]）
    重新计 token
    直到 < context_size * trigger_ratio
然后重试 generate_structured_output
```

即**逐步丢弃最旧消息**，直到剩余内容能塞进压缩调用。这是一种"尽力而为"——保不住最老的信息，但保证压缩本身不崩。

压缩成功后：
- 若配置了 `Offloader`，把 `msgs_to_compress` offload 到文件，summary 里追加引用路径（`:471-480`）：
  ```
  <system-reminder>The compressed context is offloaded to '{path}'...</system-reminder>
  ```
- 清理不再被引用的 Read 文件缓存（`:482`，`_clear_unreserved_read_cache`）。
- `self.state.context = msgs_to_reserve`（`:485`）——**旧消息从 live context 移除**，只留近期消息 + summary。

### 问题 5：单个工具结果过大

这是和"整 context 压缩"独立的另一条线。每个工具执行完，结果都经过 `_split_tool_result_for_compression`（`_agent.py:1828`）检查：

```python
n_tokens = count_tokens(工具结果)
if n_tokens <= cfg.tool_result_limit:   # 默认 50000 token（_config.py:112）
    return block  # 不大，原样保留
# 太大，截断
```

截断逻辑（`:1862-1955`）：
- 从结果末尾往前找边界，让保留的前缀 ≤ `tool_result_limit`。
- 边界 block 若是 `TextBlock`，**按 token 比例截断文本**（`:1888-1922`）。
- 截断后在保留部分追加提示（`:1471-1514`）：
  ```
  <<<TRUNCATED>>>
  <system-reminder>The remaining content has been omitted for limited context.
  You can refer to the file in '{path}' for the truncated content if needed.</system-reminder>
  ```
- 被截掉的尾部 offload 到 workspace 文件（`offloader.offload_tool_result`，`:1482`）。

🔑 模型看到的是"前面一部分 + 截断提示 + 文件路径"，需要细节时可以主动用 Read 工具去读那个文件。这就是 **offload + reminder 模式**：不丢信息，但把它移出 context window。

### 问题 6：两种 offload 别混淆

⚠️ 框架里有**两个名字相似但完全不同**的机制：

| 机制 | 触发条件 | 位置 | 作用 |
|------|---------|------|------|
| **size-based 截断** | 单个工具结果 > 50000 token | `_agent.py:1828` | 把大结果的尾部存文件 |
| **time-based 后台 offload** | 工具执行 > 10 秒 | `app/middleware/_tool_offload_middleware.py` | 把慢工具转后台任务 |

第二个是**服务层中间件**（第7章会讲），它把执行慢的工具变成后台任务，agent 立即拿到一个"工具在后台跑，别轮询"的占位结果，真正结果完成后通过 inbox + wakeup 再送达。它处理的是"慢"，不是"大"。

🔑 口诀：**大 → 截断 + offload 文件；慢 → 后台任务 + 唤醒**。

`Offloader` 协议（`workspace/_offload_protocol.py:8`）只有两个方法：
- `offload_context(session_id, msgs) -> str`：存压缩掉的旧消息（JSONL）。
- `offload_tool_result(session_id, tool_result) -> str`：存截断的工具结果尾部（txt）。

`LocalWorkspace` 实现（`_local_workspace.py:495`、`:550`）把它们写到 `{workdir}/sessions/{session_id}/` 下。

## 五、一次完整压缩的流程图

```
每次 reasoning 开头（_agent.py:608）
  │
  ▼
compress_context（中间件洋葱）→ _compress_context_impl
  │
  ├─ count_tokens(全部输入) < 0.8 * context_size ?
  │     是 → 直接返回，不压缩
  │     否 ↓
  │
  ├─ _split_context_for_compression
  │     从后往前累计，保留 10% 近期消息
  │     block 级精确切分
  │     保护 tool_call/tool_result 配对
  │
  ├─ generate_structured_output(压缩侧) → SummarySchema
  │     失败且溢出 → 逐步丢最旧消息重试
  │
  ├─ state.summary = 渲染后的摘要 + offload 引用路径
  ├─ offload 压缩侧消息到文件
  ├─ 清理无用 Read 缓存
  └─ state.context = 保留的近期消息
```

## 六、本章小结

🔑 四句话：
1. **context 是 `state.context`（list[Msg]）**，system prompt 不在其中，每次重生成。
2. **压缩在每次 reasoning 前判断**，超 `0.8 * context_size` 才触发，生成**结构化摘要**存进 `state.summary`。
3. **切分保护 tool_call/result 配对**，失败时逐步丢最旧消息重试——尽力而为。
4. **大工具结果单独截断 + offload**，留 reminder 路径；**慢工具**走另一套后台机制（第7章）。
