# 第6章 工具系统

> 源码位置：`src/agentscope/tool/`。这一章回答："agent 怎么调用外部能力？普通函数、MCP 工具、内置工具怎么统一？工具能并发吗？"

## 一、概念引入

让 LLM 用工具（function calling）是 agent 区别于聊天机器人的核心。但工具系统要处理的问题比"调个函数"复杂得多：

- **异构来源**：Python 函数、MCP 协议工具、框架内置工具（Bash/Read/Write），接口各不相同。
- **流式输出**：工具可能产出一大段流式数据（如 grep 实时匹配），不能等全部完成才返回。
- **并发安全**：多个工具能同时跑吗？只读工具和写工具怎么分组？
- **状态注入**：有些工具需要访问 agent 状态（如任务列表工具），怎么传进去？
- **权限**：哪些工具调用前要问用户？（第8章详讲）
- **错误处理**：工具抛异常、被取消，怎么变成模型能理解的结果？

AgentScope 的解法：**统一 `ToolBase` 抽象 + `Toolkit` 分发器 + `ToolChunk/ToolResponse` 流式协议**。


## 三、经典问题

1. 模型说要调工具，框架怎么找到对应工具并执行？
2. 工具的输出怎么从"流式"变成"最终结果"？
3. 普通函数、MCP 工具、内置工具怎么统一成一个接口？
4. 多个工具调用，哪些能并发、哪些必须串行？
5. 工具执行出错或被用户取消，模型看到什么？

## 四、源码剖析

### 问题 1：Toolkit 的分发

`Toolkit.call_tool`（`_toolkit.py:225-388`）是核心分发器。docstring（`:232`）点明：**"累积过程发生在这个函数里"**——工具本身只产出增量 chunk，`call_tool` 负责累积成完整响应。

流程：
1. `tool_response = ToolResponse(id=tool_call.id)`（`:247`）——先建空响应。
2. `_get_available_tools(activated_groups)`（`:250`）——按激活的工具组构建可用工具字典。
3. **工具不存在/未激活**（`:254-291`）：产出错误 `ToolChunk`，附上"如何激活工具组"的提示，`return`。
4. `kwargs = _json_loads_with_repair(tool_call.input)`（`:299`）——解析模型给的 JSON 参数（带修复）。
5. **状态注入**（`:302-307`）：若 `is_state_injected`，把 `state` 作为 `_agent_state` 注入 kwargs。
6. 调用 `tool_func(**kwargs)`，归一化返回值（`:316-337`）。
7. `finally: yield tool_response`（`:386`）——**累积的完整响应永远是最后产出**。

🔑 工具查找（`_get_available_tools`，`:469`）按"工具组"组织：默认有 `basic` 组，激活哪些组由 agent 配置。还内置两个元工具：`SkillViewer`（有技能时）和 `ResetTools`（多于一个组时，用来切换激活组）。这让 agent 能**动态切换工具集**——比如先查资料（开搜索组），再写代码（关搜索开编辑组）。

### 问题 2：ToolChunk → ToolResponse 流式协议

定义在 `_response.py`。两个角色：

- **`ToolChunk`**：增量片段。工具边跑边 yield，可能是 `str`、`TextBlock`、`DataBlock`，带一个 `state`（RUNNING/ERROR/INTERRUPTED/...）。
- **`ToolResponse`**：累积的完整结果。`append_chunk`（`:55-144`）把 chunk 累积进 content，按 id 合并连续 `TextBlock`、拼接 base64 数据，**state 只会变坏不会变好**（ERROR 不会被后续 RUNNING 覆盖）。

```
工具 __call__ 产出:  chunk1 → chunk2 → chunk3 → ... 
                            │ append_chunk 累积
                            ▼
              ToolResponse（最终，含完整 content + 最终 state）
```

💡 为什么这么设计？因为前端要**逐块渲染**（grep 每匹配一行就显示），但 context 里要存**完整结果**。`call_tool` 既向上 yield 增量（转成 `ToolResultTextDeltaEvent`），又在内部累积，最后 yield 完整 `ToolResponse`（转成 `ToolResultBlock` 存 context）。

### 问题 3：三种工具的统一

`ToolBase`（`_base.py:94`）是抽象基类，关键方法：

| 方法 | 作用 | 默认行为 |
|------|------|---------|
| `call(*args, **kwargs)` | **工具实现点**，子类重写 | 抛 NotImplementedError |
| `__call__(*args, **kwargs)` | **真正调用入口**，处理中间件洋葱 + 归一化 | 包装 `call` |
| `check_permissions(input, ctx)` | 权限判定（第8章） | 抽象，子类实现 |
| `check_read_only(input)` | 是否只读 | 返回 `self.is_read_only` |
| `match_rule(rule, input)` | 规则匹配 | `rule is None` 则全匹配 |

类属性标记工具特性：`is_concurrency_safe`、`is_read_only`、`is_external_tool`、`is_state_injected`、`is_mcp`。

三种实现：

**FunctionTool**（`_adapters.py:31`）——包普通 Python 函数：
- 默认 `is_concurrency_safe=True`、`is_read_only=False`。
- `check_permissions` 默认 **ASK**（":90"，"自定义函数工具必须显式被用户允许"）。
- `call` 把函数返回值（标量/gen/async-gen）统一转成 `ToolChunk`，非字符串 JSON 序列化。

**MCPTool**（`_adapters.py:167`）——包 MCP 协议工具：
- `is_mcp=True`，默认 `is_concurrency_safe=False`（保守）。
- `is_read_only` 取自 MCP 工具的 `annotations.readOnlyHint`。
- 名字 sanitized 成 `mcp__{mcp名}__{工具名}`（`:218`）。
- `check_permissions`：只读→ALLOW，否则 ASK（`:266`）。

**内置工具**（`_builtin/`）——Bash/Read/Write/Edit/Glob/Grep：
- 各自重写 `check_permissions` 做精细判定（如 Bash 的 tree-sitter 分析，第8章）。
- Read 有文件缓存（`state.tool_context.read_file_cache`，按 mtime 失效）。

🔑 统一的关键：**不管来源，最终都实现 `call` 产出 `ToolChunk`，`Toolkit` 用同一套累积逻辑处理**。这就是适配器模式的价值。

### 问题 4：并发分组

第2章提到 `_batch_tool_calls`（`_agent.py:1101`）。分组逻辑（`:1117-1136`）：

- `tool.is_concurrency_safe == True` → 进 **concurrent** 批。
- `False` → 进 **sequential** 批。
- 未注册的工具也当 concurrent（注释说"不会有副作用，会被 acting 拦住"）。

⚠️ **`is_read_only` 不参与并发分组**！它只被权限引擎用（`_base.py:258`）。两个属性服务不同层：`is_concurrency_safe` 管"能不能同时跑"，`is_read_only` 管"要不要问用户"。

**串行执行**（`_execute_sequential_tool_calls`，`:1140`）：按序跑，遇到 `RequireUserConfirmEvent`/`RequireExternalExecutionEvent` 立即 break，剩余工具跳过。

**并发执行**（`_execute_concurrent_tool_calls`，`:1187`）：
- `asyncio.gather(*tasks, return_exceptions=True)`——`return_exceptions=True` 保证**一个失败不取消其他**（`:1200` 文档强调）。
- 所有任务把事件塞进共享 `asyncio.Queue`，主循环 drain。
- 全部完成后，收集异常，若有则 `raise ExceptionGroup(...)`（`:1266`）。
- sentinel 在 `gather` 返回后才放队列，保证事件流完整。

💡 这是个值得学的并发模式：**gather(return_exceptions=True) + 共享队列 + sentinel**，既并发又保证事件不丢、失败不连坐。

### 问题 5：错误与取消

异常处理在 `call_tool`（`:339-384`）：
- `McpError` → 错误 `ToolChunk`。
- `DeveloperOrientedException`（框架内部错）→ 重新抛出（不该对模型隐藏）。
- 其他 `Exception` → 错误 `ToolChunk`，内容是 `str(e)`（模型能看到错误信息，自己决定下一步）。
- `asyncio.CancelledError` → `INTERRUPTED` 状态 chunk，"interrupted by the user"。

🔑 错误不崩溃 agent，而是变成 `ToolResultBlock(state=ERROR)` 写进 context——模型看到"工具失败了，错误是 XXX"，可以重试或换方案。这是 agent 鲁棒性的关键：**工具失败是正常的，agent 应该学会处理**。

## 五、工具级中间件（onion）

`ToolBase` 还支持**工具级中间件**（`ToolMiddlewareBase`，`_base.py:36`），用洋葱模型包 `on_tool_call`。这是较新的特性（PR #1754），允许在单个工具调用前后插逻辑（如日志、参数改写、结果后处理）。`__call__`（`:209-248`）在有中间件时构建 `execute_chain`。

📝 **思考题**：
1. `FunctionTool` 默认 `check_permissions=ASK`，而 `MCPTool` 只读时 `ALLOW`。为什么对自定义函数更保守？（提示：自定义函数能做任何事，MCP 工具至少有 `readOnlyHint` 元信息）
2. 并发执行用 `return_exceptions=True`，如果 3 个工具里 1 个抛异常，另外 2 个的结果会丢吗？去 `:1200-1273` 验证。
3. 工具的 `input` 是 JSON 字符串，用 `_json_loads_with_repair` 解析。为什么需要 "repair"？想想模型流式输出时 JSON 可能不完整。

## 六、本章小结

```
ToolBase（call 产出 ToolChunk）
   ├─ FunctionTool  包普通函数（默认 ASK）
   ├─ MCPTool       包 MCP 工具（只读 ALLOW，否则 ASK）
   └─ 内置工具      Bash/Read/Write/...（精细权限判定）
          │
   Toolkit.call_tool（查找 + 解析参数 + 状态注入 + 累积 + 错误处理）
          │
   is_concurrency_safe ?
     ├─ True  → concurrent 批（gather + 队列 + sentinel）
     └─ False → sequential 批（遇 HITL 即 break）
```

🔑 四句话：
1. **统一 `ToolBase` 抽象**，三种来源（函数/MCP/内置）殊途同归产出 `ToolChunk`。
2. **`Toolkit.call_tool` 负责累积**，工具只产增量，完整 `ToolResponse` 最后才 yield。
3. **并发看 `is_concurrency_safe`**（非 `is_read_only`），gather + return_exceptions 保证失败不连坐。
4. **工具错误变 `ToolResultBlock(state=ERROR)`**，不崩溃 agent，让模型自己处理。
