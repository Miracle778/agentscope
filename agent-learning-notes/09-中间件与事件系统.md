# 第9章 中间件与事件系统

> 源码位置：`src/agentscope/middleware/_base.py`、`src/agentscope/agent/_agent.py`（中间件装配）、`src/agentscope/event/_event.py`。这一章回答："框架怎么做到可插拔？事件怎么流到前端？"

## 一、概念引入

一个 agent 框架如果把这些都写死在主循环里会很僵：
- 长期记忆（reply 前检索、后写回）
- 预算控制（超 token 就停）
- 分布式追踪（OTel span）
- 工具超时 offload（慢工具转后台）
- 跨 agent inbox drain

AgentScope 的解法是**中间件洋葱模型**：主循环只保留 ReAct 骨架，所有横切关注点做成中间件，层层包裹骨架的每个阶段。同时，每个阶段产生**事件**，事件流既驱动中间件，又通过总线送到前端。

## 四、源码剖析

### 问题 1：6 个 hook 的位置

`MiddlewareBase`（`middleware/_base.py`）定义 6 个 hook，对应 ReAct 循环的 6 个切入点：

| Hook | 位置 | 包裹什么 | 模式 |
|------|------|---------|------|
| `on_reply` | 一次完整回复最外层 | 整个 ReAct 循环 | 洋葱 |
| `on_reasoning` | 每次推理步 | 调模型 + 流式输出 | 洋葱 |
| `on_acting` | 每次工具执行 | 单个工具调用 | 洋葱 |
| `on_model_call` | 模型 API 调用 | 单次 LLM 请求 | 洋葱 |
| `on_compress_context` | 上下文压缩 | 压缩实现 | 洋葱 |
| `on_system_prompt` | 系统 prompt 构建 | prompt 字符串 | **变压器** |

💡 前 5 个是洋葱：中间件可以 `yield` 透传下游结果，在 yield 前后做事（如 reply 前检索、reply 后写回）。第 6 个是变压器：接收上一个中间件产出的 prompt 字符串，返回改写后的字符串，串行流水线。

### 问题 2：洋葱 vs 变压器

**洋葱模型**（`on_reply` 等）：中间件像洋葱皮，`next_handler` 是内层。典型结构：

```python
async def on_reply(self, agent, input_kwargs, next_handler):
    # yield 之前：reply 前的逻辑（如检索记忆）
    async for item in next_handler(**input_kwargs):   # 透传内层
        # yield 之前（每次）：可改写事件
        yield item
    # yield 之后：reply 后的逻辑（如写回记忆）
```

🔑 关键：中间件能同时看到"前"和"后"——`next_handler` 之前是前置逻辑，迭代完之后是后置逻辑。这就是 mem0 能"reply 前检索、reply 后写回"的原理（第5章）。

**变压器模型**（`on_system_prompt`）：没有 `next_handler`，而是接收当前 prompt，返回新 prompt（`_base.py:210-230`）：

```python
async def on_system_prompt(self, agent, current_prompt) -> str:
    return current_prompt + "\n你可以用 search_memory 工具查记忆"
```

`_get_system_prompt`（`_agent.py:1999-2000`）串行应用所有 `on_system_prompt` 中间件。💡 为什么 system prompt 用变压器而非洋葱？因为它是**纯字符串变换**，没有"流式事件"要透传，变压器更简洁。

### 问题 3：注册与分桶

中间件在 `Agent.__init__`（`_agent.py:167-184`）按实现的 hook **分桶注册**：

```python
for mw in middlewares:
    if hasattr(mw, "on_reply"): self._reply_middlewares.append(mw)
    if hasattr(mw, "on_reasoning"): self._reasoning_middlewares.append(mw)
    # ... 每种 hook 一个桶
```

🔑 一个中间件可以**实现多个 hook**（如 `Mem0Middleware` 同时实现 `on_reply`/`on_system_prompt`/`list_tools`），它会被分到多个桶里。运行时各 hook 独立组装责任链。

责任链由 `execute_chain`（`_agent.py:510-539`）递归组装：每个中间件包一层，最内层是 `_reply_impl`（骨架）。没有中间件时直接调骨架——零开销。

### 问题 4：26 种事件

`EventType`（`event/_event.py:20-60`）定义 26 种事件，覆盖 agent 生命周期全貌：

| 阶段 | 事件 |
|------|------|
| 回复生命周期 | `REPLY_START` / `REPLY_END` |
| 模型调用 | `MODEL_CALL_START` / `MODEL_CALL_END`（带 token 用量） |
| 文本块 | `TEXT_BLOCK_START` / `_DELTA` / `_END` |
| 思考块 | `THINKING_BLOCK_*` |
| 工具调用 | `TOOL_CALL_START` / `_DELTA` / `_END` |
| 工具结果 | `TOOL_RESULT_START` / `_TEXT_DELTA` / `_DATA_DELTA` / `_END`（带 SUCCESS/ERROR/DENIED 状态） |
| 数据块 | `DATA_BLOCK_*` |
| 提示块 | `HINT_BLOCK`（跨 agent 消息、记忆注入） |
| HITL | `REQUIRE_USER_CONFIRM` / `USER_CONFIRM_RESULT` / `REQUIRE_EXTERNAL_EXECUTION` / `EXTERNAL_EXECUTION_RESULT` |
| 超限 | `EXCEED_MAX_ITERS` |
| 自定义 | `CUSTOM`（状态变更、团队变更） |

💡 事件由 agent 循环 `yield`（如 `_agent.py:584` 的 `ReplyStartEvent`）。在服务层，每个事件被 `session_publish_event` 发到 message bus（`_chat.py:387`），既存进 replay log（新订阅者能回看历史），又通过 pub/sub 实时推给 SSE 前端。

### 问题 5：中间件与事件的关系

两者协作但不同：

- **中间件**是"过程中的钩子"——它在事件**产生时**拦截/改写。比如 `on_reasoning` 中间件能改写模型输出的事件流。
- **事件**是"过程的产物"——中间件透传或产生的事件，最终流向前端。

🔑 一个微妙点：`on_acting` 的 docstring（`_base.py:120-125`）明确说**权限检查在 on_acting 之外**——即中间件看不到权限决策（见第8章和 `issue-draft/` 的 issue）。这是当前中间件能力的一个边界。

📝 **思考题**：
1. 如果要加一个"每次回复前检查用户余额，不足就拒绝"的中间件，该实现哪个 hook？在 yield 前还是后做事？
2. `on_model_call` 和 `on_reasoning` 都包模型调用，区别在哪？（提示：重试/fallback 在哪层？看 `_agent.py:2034`）
3. 去数一下 `event/_event.py` 里的事件是不是正好 26 种，并分类记忆。

## 五、本章小结

🔑 四句话：
1. **6 个 hook** 覆盖 ReAct 循环所有切入点，前 5 个洋葱、system_prompt 变压器。
2. **洋葱中间件能看前后**（yield 前后），变压器是纯字符串流水线。
3. **中间件按 hook 分桶**，可多 hook 复用，`execute_chain` 递归组装责任链。
4. **26 种事件**由循环 yield，经 message bus 推前端，中间件可拦截改写。
