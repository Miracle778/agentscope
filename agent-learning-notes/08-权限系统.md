# 第8章 权限系统

> 源码位置：`src/agentscope/permission/`、`src/agentscope/tool/_builtin/_bash.py`、`_bash_parser.py`。这一章回答："agent 要执行危险操作时，谁拦、怎么拦、拦不住怎么办？"

## 一、概念引入

让 agent 自由调工具很危险——`rm -rf /`、读 `~/.ssh/id_rsa`、把信用卡号 POST 出去。业界两种思路：

- **运行时拦截**：工具执行前问"这个操作安全吗"，不安全就拦或问人。
- **沙箱隔离**：让操作只能影响沙箱，拦不住也无害（见第7章 workspace）。

AgentScope 两者都做，且**组合使用**：沙箱是后端防线（Docker/E2B），权限引擎是前置闸门（对所有 backend 生效）。这一章讲权限引擎。

## 三、经典问题

1. 五种权限模式分别是什么？什么时候用？
2. 规则的优先级是什么？用户能"永久允许"某个工具吗？
3. 什么是 "bypass-immune"？为什么需要它？
4. Bash 命令怎么判断危不危险？静态分析靠谱吗？

## 四、源码剖析

### 问题 1：五种模式

`PermissionMode`（`_types.py`）+ `PermissionEngine` 的 5 个 `_check_*` 方法（`_engine.py:104-114` 分发）：

| 模式 | 语义 | 典型场景 |
|------|------|---------|
| `DEFAULT` | 默认：危险操作 ASK，只读自动 ALLOW，无规则则 ASK | 交互式，问用户 |
| `EXPLORE` | 只读：非只读直接 DENY，忽略 allow 规则 | 让 agent 只看不改 |
| `ACCEPT_EDITS` | 接受编辑：工作目录内的写操作自动 ALLOW | 信任 agent 改文件 |
| `BYPASS` | 绕过：跳过所有 bypass-immune，默认 ALLOW | ⚠️ 仅限沙箱环境 |
| `DONT_ASK` | 不问：把所有 ASK 转成 DENY | 无人值守，宁可不执行 |

⚠️ `BYPASS`（`_engine.py:337-410`）是危险模式——它**故意跳过** `rm -rf /`、命令注入等 bypass-immune 检查（docstring 说"仅用于沙箱"）。但代码**不检测**运行环境是否真沙箱，所以 LocalWorkspace + BYPASS = 完全裸奔。

### 问题 2：规则优先级

规则存在 `PermissionContext` 的三个桶（`_context.py`）：`allow_rules`/`deny_rules`/`ask_rules`，按 tool_name 索引。

🔑 **优先级硬编码为 deny > ask > allow**（所有模式一致，`_engine.py` 每个 `_check_*` 都先查 deny 再 ask 再 allow）。

规则怎么来？唯一运行时来源是 `engine.add_rule`（`_engine.py:48`），它只在用户确认工具调用时被调（`_agent.py:1029`）——用户点"允许并记住"，规则就持久化到 session state，下次同类操作自动放行。

规则匹配由 `tool.match_rule(rule_content, input)` 决定（`_base.py:282`）：
- Bash（`_bash.py:395`）：支持前缀匹配 `git:*`、通配符正则、子串匹配。
- Read/Write/Edit：`fnmatch` 文件路径。
- 其他工具：默认只支持 tool-name 级规则（`rule_content is None` 匹配全部）。

💡 docstring 承诺的 `userSettings`/`projectSettings` 全局规则存储**尚未实现**——规则只活在 session 内，新 session 不继承。这是个已知功能缺口。

### 问题 3：bypass-immune

`PermissionDecision`（`_decision.py:10`）有个 `bypass_immune: bool` 字段。

💡 设计意图：有些安全检查**即使 BYPASS 模式也不该跳过**——比如 `rm -rf /`、命令注入。这些检查产生 `behavior=ASK, bypass_immune=True` 的决策。

- 在 `DEFAULT`/`ACCEPT_EDITS` 等模式：bypass-immune 的 ASK 正常触发，问用户。
- 在 `BYPASS`（`_engine.py:390-398`）：**故意忽略** bypass-immune，继续 ALLOW——因为 BYPASS 的语义就是"我信任环境，别拦"。

🔑 这是个"信任边界"的设计：bypass-immune 标记"这个操作危险到连普通 allow 规则都不该覆盖"（`_is_safety_ask`，`_engine.py:527`），但 BYPASS 是用户显式放弃所有保护的开关，所以连它也跳过。这把"多危险"和"多信任"解耦了。

### 问题 4：Bash 静态分析

`Bash.check_permissions`（`_bash.py:206`）是个分层检查器，用 **tree-sitter** 解析 bash AST（`_bash_parser.py`）：

```
0. 注入风险检测（command_substitution $(...)、subshell、控制流）→ bypass-immune ASK
1. 只读判定（ls/cat 等 + 无重定向）→ 自动 ALLOW
2. 危险命令模式（rm -rf, dd, mkfs...）→ bypass-immune ASK
3. sed 约束（拒绝 w/W/e 命令、危险文件 -i）→ bypass-immune ASK
4. 危险配置路径（~/.bashrc, /etc/passwd...）→ bypass-immune ASK
5. 危险删除路径（rm /, rm ~, rm /usr...）→ bypass-immune ASK
6. ACCEPT_EDITS 工作目录内自动放行
否则 → PASSTHROUGH（交给引擎规则）
```

⚠️ 静态分析的局限（值得读源码时注意）：
- 危险命令是**子串匹配**（`_bash.py:450`），`rm  -rf`（多空格）、`rm -fr`、`rm --recursive --force` 可绕过。
- `tee` 被当只读（`_bash_parser.py:35`），`cat f | tee /etc/passwd` 会误判为只读。
- 引号内的路径不被提取（`_bash_parser.py:573`），`rm "~/.bashrc"` 可能逃过路径检查。
- `$VAR` 展开是运行时的，静态分析无法知道 `$HOME` 指向哪。

💡 这些局限说明：**静态分析是"降低风险"而非"绝对安全"**。真正兜底的是沙箱（第7章 workspace）。权限引擎是"快速过滤明显的危险"，沙箱是"过滤不掉的也跑不出容器"。

### 问题 5：权限与 ToolCallState 联动

回顾第1章的 `ToolCallState`，权限决策驱动它的转换（`_agent.py:1371-1419`）：

```
check_permission 返回:
  ASK/PASSTHROUGH → state 置 ASKING → yield RequireUserConfirmEvent → 暂停
  DENY            → _handle_error_tool_call(state=DENIED) → finished
  ALLOW           → state 置 ALLOWED → 执行
```

用户确认后（`_agent.py:1014-1029`）：state 从 ASKING → ALLOWED，并 `add_rule` 记住用户的决定。下次同类操作，规则命中 ALLOW，直接放行不再问。

🔑 权限决策是**一次性的**（每次工具调用都 check），但规则是**累积的**（用户授权过就记住）。这就是 HITL 的"渐进信任"：一开始多问，用户烦了就"永久允许"，agent 逐渐获得自主权。

📝 **思考题**：
1. 为什么 EXPLORE 模式**忽略 allow 规则**（`_engine.py:189`）？想想"只读模式"的安全语义。
2. BYPASS 跳过 bypass-immune，那 BYPASS 还剩什么保护？答案：只剩用户预先设的 deny/ask 规则。去 `_engine.py:337-410` 确认。
3. 如果要让权限决策可被审计（记录每次 allow/deny），应该在哪里加 hook？这正好是本仓库 `issue-draft/` 里那个 issue 的主题——权限决策目前对中间件不可见。

## 五、本章小结

🔑 四句话：
1. **五种模式**覆盖从"全问"到"全放"的信任光谱，BYPASS 是危险开关。
2. **deny > ask > allow** 硬优先级，规则由用户确认累积，但目前只活在 session 内。
3. **bypass-immune** 标记"连普通 allow 都不该覆盖的危险"，但 BYPASS 连它也跳过。
4. **Bash 静态分析靠 tree-sitter**，快速过滤明显危险，但有子串匹配等局限——真正兜底是沙箱。
