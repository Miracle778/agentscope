# 第1章 消息与内容块（Msg / ContentBlock）

> 源码位置：`src/agentscope/message/`。这是整个框架的"货币"——所有模块都在传递 `Msg`。读懂这一章，后面每章都会轻松。

## 一、概念引入

一个最朴素的 agent 调用长这样：

```python
response = client.chat.completions.create(
    messages=[{"role": "user", "content": "你好"}],
)
```

为什么 AgentScope 不直接用这种 `{"role", "content"}` 字典列表，而要造一套 `Msg` + `ContentBlock` 体系？因为真实 agent 需要处理：

- **多家 provider**：OpenAI、Anthropic、Gemini……每家的消息格式都不一样（Anthropic 把 tool_use 放在 content 数组里，OpenAI 用单独的 tool_calls 字段；Gemini 没有 system role）。
- **多模态**：一张图、一段音频，怎么和文本混在一条消息里？
- **工具调用**：模型说要调工具、工具返回结果，这是两段结构化数据，不是纯文本。
- **推理过程**：有些模型（Claude）会输出 thinking，要不要存？
- **框架内部信号**：记忆注入、跨 agent 消息，这些是"给模型看的提示"，但不是用户说的话，怎么标记？

如果直接用 OpenAI dict，每加一个 provider 就要 if-else 一堆格式分支，业务逻辑里到处渗透 provider 细节。AgentScope 的解法是：**定义一套统一的、provider 无关的 `Msg`，所有业务逻辑只操作 `Msg`，直到真正发请求前一刻，才由 `formatter` 翻译成各家格式**。

## 二、源码地图

```
message/
├── _block.py     ContentBlock 六兄弟 + 两个状态枚举
├── _base.py      Msg / UserMsg / AssistantMsg / SystemMsg / Usage
└── __init__.py   统一导出
```

入口：从 `__init__.py`（`message/__init__.py:1`）看导出清单，就知道这个模块的全部公共 API。

## 三、经典问题

1. `Msg` 到底长什么样？`content` 是字符串还是列表？
2. 六种 `ContentBlock` 分别什么时候产生？谁产生？
3. `HintBlock` 是干什么的？为什么记忆和跨 agent 消息都用它？
4. 工具调用有"状态"，这些状态怎么流转？为什么需要状态机？
5. 多模态内容（图片）怎么统一表示？

## 四、源码剖析

### 问题 1：`Msg` 的结构

`Msg` 定义在 `message/_base.py:66`（Pydantic BaseModel）。核心字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | `str` | 说话者名字（不是 role，是具体 agent 名，多 agent 场景用来区分谁说的） |
| `content` | `str \| list[ContentBlock]` | **可以是纯字符串，也可以是 block 列表** |
| `role` | `Literal["user","assistant","system"]` | 角色 |
| `id` | `str` | 消息唯一 id |
| `usage` | `Usage` | token 用量（input/output/cache 等） |

🔑 **`content` 是 `str | list[ContentBlock]`**——这是关键设计。简单文本消息用 `str`（省事），复杂消息用 block 列表。三个便捷子类：`UserMsg`/`AssistantMsg`/`SystemMsg`（`message/__init__.py:18`）只是预设了 `role`。

### 问题 2：六种 ContentBlock

全部定义在 `message/_block.py`，都是 Pydantic BaseModel，用 `type` 字面量做判别：

| Block | 行号 | 谁产生 | 作用 |
|-------|------|--------|------|
| `TextBlock` | `_block.py:11` | 模型输出 / 工具结果 | 普通文本 |
| `ThinkingBlock` | `_block.py:22` | 模型输出（Claude 等） | 推理过程，`extra="allow"` 保留 provider 特有字段如 `signature` |
| `DataBlock` | `_block.py:67` | 模型输出 / 工具结果 | 二进制（图/音/视频），`source` 是 `Base64Source`(`:40`) 或 `URLSource`(`:51`) |
| `ToolCallBlock` | `_block.py:114` | 模型输出 | 模型要调工具，含 `name`/`input`(JSON 字符串)/`state` |
| `ToolResultBlock` | `_block.py:171` | agent 执行工具后 | 工具返回，含 `tool_call_id`/`output`/`state` |
| `HintBlock` | `_block.py:81` | 框架内部（记忆/团队消息） | 给模型的提示，发请求时转成 user message |

💡 **注意 `ToolCallBlock.input` 是 JSON 字符串，不是 dict**（`_block.py:129`）。因为流式输出时模型是逐 token 生成参数的，存成字符串方便累积，解析推迟到真正执行工具时（`_agent.py:1339` 的 `_json_loads_with_repair`）。

### 问题 3：HintBlock——框架内部的"悄悄话"

看 `HintBlock` 的 docstring（`_block.py:81-89`）：

> A block used to provide instructions or hints to the LLM during the reasoning-acting loop. When passed to the LLM API, **the hint block is converted into a user message**.

它有两个字段值得注意：
- `hint: str | list[TextBlock | DataBlock]`（`:93`）——可以是纯文本，也可以是多媒体。
- `source: str | None`（`:98`）——发送者。跨 agent 消息里是发送者名字（如 `"alice"`）。

为什么需要它？因为有两种"给模型看的提示"**不是用户真正说的话**，如果直接塞成 user message 会污染对话语义：

1. **长期记忆注入**：mem0 中间件检索到的记忆，作为 `name="memory"` 的 assistant 消息里的 HintBlock 注入（见第5章）。
2. **跨 agent 消息**：`TeamSay` 工具把消息包装成 `<team-message from="alice">...</team-message>` 的 HintBlock，推到对方 inbox（见第7章）。

🔑 HintBlock 是框架"在对话里夹带私货"的统一通道——既能在 context 里和正常消息共存，又在格式化时被转成 user message 让模型看到，但不冒充真实用户发言。

### 问题 4：ToolCallState 状态机

这是理解"人在环中"（HITL）的核心。`ToolCallBlock.state`（`_block.py:131`）有 5 个值，`_block.py:140-155` 的 docstring 直接画了状态转换图：

```
pending
  ├── permission DENY / 输入校验失败 ──► finished
  ├── permission ASK ─────────────────► asking
  │       ├── 用户拒绝 ────────────────► finished
  │       └── 用户批准 ────────────────► allowed
  └── permission ALLOW ────────────────► allowed

allowed
  ├── 本地工具 ──(执行)────────────────► finished
  └── 外部工具 ────────────────────────► submitted

submitted
  └── 收到 ExternalExecutionResultEvent► finished
```

💡 **为什么工具调用要有状态？** 因为 agent 循环可能在工具执行中途**暂停**：

- 模型说要 `rm -rf /` → 权限判定为 ASK → state 置为 `ASKING` → agent 生成 `RequireUserConfirmEvent` 后**整个 reply 结束**，把控制权还给前端。
- 用户点了"允许" → 前端带着 `UserConfirmResultEvent` 再次调用 `reply` → agent 从断点续接，发现 state 是 `ASKING` 的工具，把它转成 `ALLOWED` 继续执行。

没有状态机，agent 重启后无法知道"这个工具调用上次进行到哪了"。这个状态机贯穿第2章（ReAct 循环）和第8章（权限），是 agent 可中断、可恢复的基石。

⚠️ 注意 `state` 在 `ASKING` 时置位**必须在 yield 事件之前**（`_agent.py:1392-1393` 有专门注释强调这点），因为外层循环一收到 `RequireUserConfirmEvent` 就会 break，yield 之后的代码不会执行。

### 问题 5：多模态统一

`DataBlock`（`_block.py:67`）用 `source` 字段统一了两种来源：

```python
class DataBlock(BaseModel):
    source: Base64Source | URLSource   # _block.py:74
```

- `Base64Source`（`:40`）：`data`(base64 字符串) + `media_type`（如 `image/png`）
- `URLSource`（`:51`）：`url` + `media_type`

这样 agent 内部永远是 `DataBlock`，不关心是 base64 还是 URL；只有 formatter 在发请求时才决定怎么塞（OpenAI 用 `image_url`，Gemini 用 `inline_data`，见第3章）。

📝 **思考题**：`ThinkingBlock` 用了 `extra="allow"`（`_block.py:30`），允许任意额外字段。为什么？去 `formatter/_anthropic_formatter.py` 找 `ThinkingBlock` 的处理，看 `signature` 字段的作用——这关系到 Claude 的 thinking 能否在多轮中正确续接。

## 五、本章小结

```
Msg (name, role, content, id, usage)
     │
     └─ content: str | list[ContentBlock]
                        ├── TextBlock      普通文本
                        ├── ThinkingBlock  推理（provider 特有字段靠 extra=allow）
                        ├── DataBlock      多模态（Base64Source | URLSource）
                        ├── ToolCallBlock  模型要调工具（带状态机）
                        ├── ToolResultBlock 工具返回（带 SUCCESS/ERROR/DENIED...）
                        └── HintBlock      框架夹带的"悄悄话"（记忆/团队消息）
```

🔑 一句话：**`Msg` 是 provider 无关的统一消息表示，`ContentBlock` 是它的积木，`HintBlock` 是框架注入信号的通道，`ToolCallState` 是 HITL 可中断恢复的基石。**
