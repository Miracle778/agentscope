# 第10章 服务化与多租户

> 源码位置：`src/agentscope/app/`。这是最后一章，回答："单进程的 `Agent` 类怎么变成支持多用户、多会话、跨进程协作的在线服务？"

## 一、概念引入

前面九章讲的 `Agent` 类，在单进程里 `agent = Agent(...); await agent.reply("你好")` 就能跑。但生产环境需要：

- **多租户**：不同用户的数据互不可见。
- **多会话**：一个用户有多个并行对话。
- **持久化**：进程重启不丢对话历史和状态。
- **跨进程**：多个 worker 进程分担负载，agent 间消息能跨进程送达。
- **后台任务**：慢工具、定时任务不阻塞主请求。

AgentScope 把这些全放进 `app/` 子包，库本身（`Agent`）保持纯净。这是个重要架构决策：**框架不绑定部署形态**，单进程库用户和服务化用户共享同一套核心抽象。

## 三、经典问题

1. 多租户怎么隔离？一个用户能读到另一个用户的数据吗？
2. 一次 chat 请求的完整生命周期是什么？状态怎么存取？
3. 多个进程同时跑同一个 session 会冲突吗？

5. 单进程 `Agent` 和服务化 `ChatService` 共享了什么、分叉了什么？

## 四、源码剖析

### 问题 1：多租户隔离

身份来自 `get_current_user_id`（`app/deps.py:17-39`），读 HTTP 头 `X-User-ID`。

⚠️ docstring 自承这是**临时方案**（"will be replaced by JWT auth"）——目前无真实鉴权，任何客户端可伪造任意 user_id。这是已知的安全缺口（生产部署必须前置真实鉴权层）。

隔离靠 **storage 按 user namespace**（`storage/_redis_storage.py`）：所有 key 前缀 `agentscope:user:{user_id}:...`，凭据、agent、session、schedule、message 各有子命名空间。`test_user_isolation`（`tests/storage_redis_test.py:127`）验证了跨用户不可见。

### 问题 2：一次 chat 的生命周期

`ChatService.run`（`_service/_chat.py`）是核心。简化流程：

```
1. 获取分布式 session 锁   session_run → acquire_lock("agentscope:session:lock:{sid}", TTL=600s)
2. 加载状态              storage.get_session → agent_state
3. 组装 agent            Agent(state=agent_state, middlewares=[InboxMiddleware,
                           ToolOffloadMiddleware, ...用户自定义])
4. 跑 reply_stream       async for event in agent.reply_stream(...):
                            session_publish_event(event)  # 发总线
                            reply_msg.append_event(event) # 存进回复 Msg
5. 持久化                storage.update_session_state(agent.state)  # 必须在锁内
                          storage.upsert_message(reply_msg)
6. 释放锁
```

🔑 几个关键点：
- **状态在锁内更新**（`_chat.py:437-446`）：注释强调必须如此，否则并发进程会加载到过期状态。
- **中间件在每次 run 注入**（`_chat.py:260-272`）：`InboxMiddleware`（跨 agent 消息）、`ToolOffloadMiddleware`（慢工具后台化）是服务层默认中间件，外加 `extra_agent_middlewares`（用户自定义，如审计）。
- **事件双重落盘**：既进 message bus 的 replay log（供 SSE 回放），又进回复 `Msg`（持久化对话历史）。

### 问题 3：并发与锁

一个 session 同时只能有一个 run 在跑，靠**双层保护**：

1. **集群级**：message bus 的分布式锁（`message_bus/_base.py:480-514`）。`session_run` 对 `agentscope:session:lock:{sid}` 加锁，TTL 600s。两个进程抢同一 session，后者排队等前者释放或租约过期。
2. **进程级**：`ChatRunRegistry.spawn`（`_chat_run_registry.py:72-77`）若本进程已有该 session 的未完成 run，抛 `RuntimeError`。

💡 这就回答了第7章的"唤醒分发器"怎么避免重复执行：wakeup dispatcher 在 spawn 前先查 `session_is_running`（即锁状态），已在跑就跳过（`_wakeup_dispatcher.py:145`）。

### 问题 4：message bus vs storage

两者都是 Redis，但职责截然不同：

| | storage | message bus |
|---|---------|-------------|
| 职责 | 持久化业务数据 | 实时协调传输 |
| 内容 | agent/session/team/credential/message/state | inbox队列/wakeup队列/事件replay log/锁/pub-sub |
| 生命周期 | 长期（可配 TTL） | 短期（ack-on-read 或 TTL） |
| 用途 | 重启后恢复 | 跨进程/跨 session 通信 |

🔑 message bus 提供 4 种原语（`message_bus/_base.py`）：
- **drain queue**（ack-on-read）：inbox、wakeup 队列——每条只取一次。
- **replay log**（带历史）：事件流——新订阅者先回看历史再接实时。
- **pub/sub**（无历史）：wakeup 信号、cancel 广播——只在线订阅者收到。
- **distributed lock**：session 运行互斥。

第7章的"inbox_push + enqueue_wakeup"就是 drain queue + pub/sub 的组合：消息进 inbox 队列（可靠），wakeup 发 pub/sub 信号（唤醒 dispatcher）。

### 问题 5：单进程 vs 服务化的分叉

共享的：`Agent` 类、`Msg`/`ContentBlock`、model/formatter/credential、tool/permission、middleware/event、ReAct 循环、上下文压缩——**前九章全部**。

服务化新增的：
- **资源模型**（user/agent/session/team/schedule）+ HTTP API。
- **跨进程协调**（message bus 的 4 原语）。
- **后台/定时执行**（scheduler + wakeup + background task）。
- **多 agent 团队**（TeamCreate/AgentCreate/TeamSay，第7章）。
- **服务层中间件**（inbox、tool offload、state change）。

💡 这就是为什么前九章能脱离 `app/` 单独学：**核心 agent 能力是部署无关的**，`app/` 只是把"单 agent 单进程"扩展成"多 agent 多进程在线服务"。理解了前九章，`app/` 就是在它们之上加"协调层"。

📝 **思考题**：
1. 如果要自建鉴权替换 `X-User-ID`，应该改 `deps.py` 的哪个函数？FastAPI 的 dependency 注入怎么配合？
2. 一个慢工具被 offload 到后台（第7章），它的结果怎么回到正确的 session？追踪：`ToolOffloadMiddleware` → inbox_push → wakeup → `WakeupDispatcher` → `ChatService.run(input_msg=None)` → `InboxMiddleware` drain。
3. 为什么 `update_session_state` 必须在分布式锁内，而 `upsert_message` 可以不在？（提示：state 是"工作内存"会被覆盖，message 是"追加日志"）

## 五、全系列总结

走到这里，你已经把 AgentScope 的核心看完了。回顾整条学习线：

```
第1章 Msg/ContentBlock  ← 统一消息表示（货币）
第2章 ReAct 循环        ← 想-做-想-做...的心脏
第3章 模型/格式化       ← 一套代码调 9 家 LLM
第4章 上下文压缩        ← 超 80% 窗口就结构化摘要 + offload
第5章 记忆系统          ← 五层：context/summary/mem0/inbox/事件
第6章 工具系统          ← Toolkit 分发 + 并发 + MCP 适配
第7章 多 agent 调度     ← 投递+唤醒+锁，星型团队
第8章 权限系统          ← 5 模式 + bypass-immune + bash 静态分析
第9章 中间件/事件       ← 6 hook 洋葱 + 26 事件流
第10章 服务化           ← 单进程 → 多租户多进程在线服务
```

🔑 贯穿全篇的三条主线：
1. **统一抽象 + 边界翻译**：`Msg` 统一消息、`formatter` 唯一翻译点、`ToolBase` 统一工具——业务逻辑零 provider/transport 渗透。
2. **可插拔 + 可观测**：中间件洋葱让记忆/预算/追踪/权限都可插拔，事件流让一切可观测可流式。
3. **异步 + 可恢复**：`ToolCallState` 状态机让 HITL 可中断恢复，inbox+wakeup+锁让跨 agent/跨进程协作可靠。
