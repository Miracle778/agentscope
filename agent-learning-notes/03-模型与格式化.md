# 第3章 模型抽象与格式化

> 源码位置：`src/agentscope/model/`、`src/agentscope/formatter/`、`src/agentscope/credential/`。这一章回答："如何用一套代码调 9 家 LLM？"

## 一、概念引入

调一家 LLM 很简单，但要在同一个 agent 框架里支持 OpenAI、Anthropic、Gemini、DashScope、DeepSeek、Moonshot、Ollama、xAI、OpenAI Responses API 九家，难点在于：

- **消息格式各异**：Anthropic 把 tool_use 放在 content 数组里；OpenAI 用顶层 `tool_calls`；Gemini 连 system role 都没有，系统提示要塞进 user 消息。
- **凭据各异**：有的 api_key，有的 host，有的要 base_url。
- **流式协议各异**：chunk 的结构、tool 参数的累积方式都不同。

AgentScope 的解法是 **三层分离**：

```
model/       —— 调用 API、处理流式 chunk、重试、结构化输出
formatter/   —— 把统一 Msg 翻译成各家请求格式（唯一翻译点）
credential/  —— 凭据对象（SecretStr 保护）
```

💡 核心思想：**业务逻辑只操作 `Msg`，formatter 是唯一的 provider 适配边界**。加一个新 provider = 对称地加三个文件，不动 agent 主循环。

## 三、经典问题

1. 一次模型调用的完整路径是什么？（agent → model → formatter → HTTP）
2. 流式输出怎么变成事件的？
3. 同一个 `Msg` 列表，OpenAI / Anthropic / Gemini 分别怎么翻译？
4. `count_tokens` 是精确的吗？它用在什么地方？
5. `generate_structured_output` 是怎么强制模型输出 JSON 的？

## 四、源码剖析

### 问题 1：一次模型调用的路径

调用链（从第2章的 `_reasoning_impl` 出发）：

```
_reasoning_impl  (_agent.py:754)
  └─ _prepare_model_input  (_agent.py:2004)   组装 [SystemMsg, (summary?), *context] + tools schema
  └─ _call_model  (_agent.py:2034)            on_model_call 中间件洋葱 + 重试 + fallback
      └─ model(...)  = ChatModelBase.__call__  (model/_base.py:158)
          └─ _call_api                          各 provider 实现
              └─ self.formatter.format(messages)   ← 唯一翻译点
              └─ client.chat.completions.create(...)  HTTP 请求
```

🔑 `_prepare_model_input`（`_agent.py:2004-2032`）组装的顺序很重要：

```python
messages = [SystemMsg(content=await self._get_system_prompt())]  # 2013
if self.state.summary:                                            # 2017
    messages.append(UserMsg(content=self.state.summary))          # 2018
messages.extend(self.state.context)                               # 2022
```

即 **SystemMsg →（可选的压缩摘要 UserMsg）→ 原始 context**。工具 schema 单独传（`_agent.py:2025`）。

💡 **system prompt 不存在 context 里**，每次模型调用都重新生成（`_get_system_prompt`，`_agent.py:1979`）。这样中间件能动态改 system prompt（如 mem0 在这里宣传记忆工具），无需改存储状态。

### 问题 2：流式输出 → 事件

`ChatModelBase.__call__`（`model/_base.py:158-218`）是重试循环：

- 按 `_get_retryable_exceptions()` 捕获可重试异常，最多 `max_retries` 次（`_base.py:198-212`）。
- 返回值有两种形态：完整的 `ChatResponse`，或 `AsyncGenerator[ChatResponse]`（流式）。

`ChatResponse` 的 `content` 是 `list[ContentBlock]`（就是第1章那些 block）。agent 在 `_reasoning_impl`（`_agent.py:800-821`）判断返回的是不是 async generator：

- 是 → 逐 chunk 迭代，最后一个 `chunk.is_last` 的作为 `completed_response`；中间 chunk 通过 `_convert_chat_response_to_event`（`_agent.py:2395`）转成 `TextBlockDeltaEvent` / `ToolCallDeltaEvent` 等流式事件。
- 否 → 直接转成事件。

🔑 这就是为什么前端能逐 token 渲染：**模型流式 chunk → ChatResponse → AgentEvent → 事件总线 → SSE 前端**。block 的 start/delta/end 事件由 `block_ids` 字典（`_agent.py:792`）跟踪，保证跨 chunk 正确开关。

### 问题 3：formatter 的三家翻译

formatter 在 `_call_api` 里、发 HTTP 请求**之前一刻**调用（如 `model/_openai_chat/_model.py:220`）。同一个 `list[Msg]`，三种翻译：

| 维度 | OpenAI | Anthropic | Gemini |
|------|--------|-----------|--------|
| 系统消息 | 顶层 `role:"system"` | 顶层 `system` 字段 | 塞进 `role:"user"`（`_gemini_formatter.py:422`） |
| assistant role | `"assistant"` | `"assistant"` | `"model"`（`:257`） |
| 工具调用 | 顶层 `tool_calls`，`arguments` 是 **JSON 字符串** | content 数组里 `{"type":"tool_use","input": dict}` | `functionCall` parts |
| 工具结果 | 单独 `{"role":"tool"}` 消息 | content 里 `{"type":"tool_result"}`，强制消息 role 变 `"user"`（`:212`） | `functionResponse` parts |
| thinking | **直接丢弃**（`:339`） | 仅当有 `signature` 才保留（`:79`） | 不支持 |
| 多模态 | `image_url`/`input_audio` | content 里 image block | `inline_data` |

⚠️ 注意几个坑：
- OpenAI 的 tool_call `arguments` 是**字符串**，Anthropic 的 `input` 是 **dict**（`_anthropic_formatter.py:141`）。
- Anthropic 的 tool_result 必须在 role 为 `"user"` 的消息里（`:212-221`），所以 formatter 会强制改 role。
- OpenAI 把 thinking **静默丢弃**（`_openai_formatter.py:339`）——所以用 GPT 时 Claude 的思考链不会保留。

💡 多 agent 场景下，formatter 还有"消息分组"逻辑（`_group_messages`，`_formatter_base.py:175`）：把连续的工具调用序列和 agent 发言块分组，便于在历史里标注"谁说的"。

### 问题 4：count_tokens 的精度与用途

`ChatModelBase.count_tokens`（`model/_base.py:297-386`）是个**粗估**：

```
token 数 ≈ UTF-8 字节数 / 4 + json.dumps(tools) 长度 + base64 数据长度/4
```

🔑 它**不是精确的**（真正的 token 数要调 tokenizer），但够用于"要不要压缩"这种阈值判断。它唯一的用途在**上下文压缩**（第4章）：判断 `estimated_tokens` 是否超过 `trigger_ratio * context_size`。

`context_size`（`_base.py:58`）每家不同：OpenAI 128000、Anthropic 200000、Gemini 1048576、Ollama 32768（默认）。可被 YAML 模型卡片覆盖（如 `claude-opus-4-8.yaml` 设为 1000000）。

⚠️ 正常模型调用**不做**硬性 context 截断——只靠压缩在 reasoning 前清理。所以如果压缩失效，超长 context 会让 API 直接报错。

### 问题 5：generate_structured_output

`ChatModelBase.generate_structured_output`（`model/_base.py:388-585`）强制模型输出符合 JSON schema 的结构化数据。默认实现 `_call_api_with_structured_output`（`:453`）的做法：

1. 把目标 schema 包装成一个**工具**（function tool）。
2. 注入 system-reminder **强制模型必须调用这个工具**。
3. 解析模型返回的 tool call input，按 schema 校验。

💡 这个方法主要被**上下文压缩**用（`_agent.py:422`）——让模型输出结构化的 `SummarySchema`（含 `task_overview`/`current_state`/`next_steps` 等字段），而不是自由文本摘要。结构化摘要更稳定、可解析。

📝 **思考题**：去 `model/_base.py:453-585` 看默认实现，再对比某家 provider 是否重写了 `generate_structured_output`（比如 OpenAI 有原生的 `response_format`）。想想：用"强制工具调用"模拟结构化输出，相比原生 JSON mode，有什么优劣？

## 五、本章小结

```
agent 只懂 Msg ──→ _prepare_model_input 组装 ──→ ChatModelBase.__call__（重试/流式）
                                                          │
                                          formatter.format ← 唯一 provider 适配点
                                                          │
                                                     HTTP 请求 → ChatResponse
                                                          │
                                          _convert_chat_response_to_event → AgentEvent
```

🔑 三句话：
1. **model / formatter / credential 三层对称分离**，加 provider = 加三个对称文件。
2. **formatter 是唯一的翻译边界**，业务逻辑零 provider 渗透。
3. **流式 chunk → ChatResponse → AgentEvent**，三层串联让前端逐 token 渲染成为可能。
